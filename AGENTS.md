# Инструкции проекта GymTracker

## Цель проекта

Создать небольшое локальное приложение для учёта тренировок на iPhone. Во время
разработки оно запускается через Expo Go, а бесплатная пользовательская поставка
выпускается как устанавливаемая PWA с офлайн-запуском. Репозиторий также служит
учебным проектом по надёжной агентской разработке. Требования находятся в
`docs/product.md`, архитектурные решения — в `docs/architecture.md`.

## Технологические ограничения

- Используй React Native, Expo и TypeScript в строгом режиме.
- Приложение должно запускаться на физическом iPhone через Expo Go.
- Общий код должен собираться для web; платформенные различия изолируй за
  явными интерфейсами и файлами платформы.
- Храни все данные локально. Backend отсутствует.
- Предпочитай библиотеки, совместимые с Expo Go.
- PWA должна запускаться офлайн после первой успешной загрузки и установки на
  домашний экран. Не считай кэш service worker хранилищем пользовательских данных.
- Не связывай формат пользовательских данных с адресом конкретного бесплатного
  хостинга. Смена origin требует явного экспорта и импорта данных.
- Не добавляй production-зависимость без объяснения её необходимости.
- Не проектируй для гипотетического масштабирования.

## Правила работы

- Перед изменениями прочитай относящиеся к задаче документы и код.
- Ограничивай изменение запрошенным пользовательским результатом.
- Самостоятельно принимай несущественные решения реализации.
- Спрашивай перед изменением поведения продукта, архитектуры, формата хранения
  или поддерживаемой версии Expo SDK.
- Не выполняй несвязанный рефакторинг и не перезаписывай чужие изменения.
- Не добавляй учётные данные, токены, файлы подписи или персональные данные.

## Проверка изменений

После изменения кода:

1. Запусти основную команду проверки репозитория.
2. Запусти целевые тесты изменённого поведения.
3. Проверь итоговый diff на несвязанные изменения.
4. Сообщи, какие проверки прошли, а какие не удалось выполнить.

Изменение UI требует ручной проверки на iPhone по сценарию текущей задачи. Для
web-изменений дополнительно проверяй установленную PWA в обычном и офлайн-режиме.
Не утверждай, что UI или PWA проверены на iPhone, если пользователь не проверил
их сам.

## Определение готовности

Задача завершена, только если выполнены критерии приёмки, прошли относящиеся к
изменению проверки, важные правила покрыты осмысленными тестами, сохранённые
данные совместимы либо мигрированы, документация актуальна, а оставшиеся
ограничения перечислены.

## Качество кода

- Отделяй правила предметной области от React-компонентов, где это оправдано.
- Предпочитай явные типы непроверенным строкам.
- Передавай даты в бизнес-логику явно для детерминированных тестов.
- Тестируй наблюдаемое поведение, а не детали реализации.
- Вес поддерживает дробные значения, повторения — положительные целые.
