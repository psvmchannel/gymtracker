# План производительности

## Цель

Сохранить быстрый отклик установленной PWA на iPhone по мере роста истории,
не усложняя хранение раньше, чем это подтверждено измерениями. Оптимизации
выполняются небольшими этапами; после каждого этапа приложение остаётся рабочим,
формат резервной копии сохраняется, а результат проверяется на прежнем и
увеличенном наборе данных.

Основной ожидаемый объём — десятки тренировок. Контрольный увеличенный объём —
200 тренировок, до 10 упражнений и до 6 подходов на упражнение. Тестовые данные
должны быть синтетическими и воспроизводимыми: генератор использует фиксированные
даты и начальное значение генерации. Для измерений нужна отдельная тестовая PWA
на другом origin, чтобы её IndexedDB и service worker были изолированы от
пользовательской установки. Пользовательское хранилище для измерений не очищается.

## Базовые сценарии и измерения

Перед первой оптимизацией нужно зафиксировать исходные результаты для web/PWA:

- открытие раздела «Тренировки»;
- открытие тренировки из истории;
- добавление, изменение и удаление подхода;
- появление предложения скопировать предыдущие подходы и само копирование;
- открытие раздела «Статистика» и смена упражнения;
- переключение метрики графика;
- объём снимка IndexedDB, число его чтений и записей за действие;
- число создаваемых элементов графика, таблицы значений и списка дат.

Измерения выполняются для 50 и 200 тренировок в production web-сборке. Главная
ручная проверка проводится в установленной тестовой PWA на используемом iPhone,
онлайн и после заполнения кэша офлайн. Наборы включают плотную и редкую историю
упражнения, архивные упражнения, пустые записи между заполненными и тренировку
с несколькими пустыми упражнениями, в том числе без предыдущих подходов.

Для каждого сценария фиксируются:

- время от действия до обратной связи и до отображения окончательного результата;
- отдельно длительность чтения снимка, вычислений и подтверждённой записи;
- число чтений и записей, размер набора и снимка;
- модель iPhone, версия iOS, идентификатор сборки и режим сети.

Первый запуск после полного закрытия приложения измеряется отдельно от повторных
действий в открытом приложении. Для повторных действий выполняется не менее
30 повторов; фиксируются медиана и 95-й процентиль. До и после изменения
используются одинаковые наборы и условия, а для мутаций — одинаковое исходное
состояние тестовых данных. Сброс набора не включается во время самого действия.

Время операций измеряется браузерными средствами разработки или временной
локальной инструментализацией, когда они доступны. Функциональные тесты с
`fake-indexeddb` не заменяют измерения установленной PWA.

Перед первой оптимизацией в `docs/checkpoint.md` фиксируются численные бюджеты
отклика и получения результата для каждого сценария на выбранном iPhone, а также
разброс базовых измерений. Если измерить сценарий не удалось, это ограничение
указывается явно. Оптимизация считается успешной, если улучшение проблемного
сценария на увеличенном наборе превышает разброс измерений, а обычный набор
не ухудшается сверх этого разброса. Когда все сценарии укладываются в бюджеты,
дальнейшие оптимизации останавливаются.

## Этап 1. Сокращение повторных чтений снимка

После каждой мутации экран тренировок сейчас заново читает список тренировок,
список упражнений и выбранную тренировку. Дополнительно он отдельно вызывает
`getPreviousSets()` для каждого пустого упражнения, и на web каждый вызов читает
весь снимок. Сейчас сохранение подхода требует `4 + E` чтений снимка: одного
внутри операции записи, трёх при обновлении экрана и по одному для `E` оставшихся
пустых упражнений.

Нужно измерить вклад этих чтений и сократить их без рассинхронизации интерфейса
и хранилища. Предпочтительный путь — возвращать из операции или одного
репозиторного запроса согласованные данные. Предложения копирования для всей
выбранной тренировки должны определяться за одно чтение снимка. Каталог
упражнений не перечитывается после изменения только подходов. Неявный
глобальный кэш для этого не требуется.

Критерии готовности:

- добавление, изменение и удаление подхода выполняют только необходимые чтения;
- число чтений снимка для предложений копирования не зависит от количества
  пустых упражнений в выбранной тренировке;
- при нажатии копирования источник и пустота упражнения повторно проверяются
  внутри атомарной операции записи; повторное нажатие не создаёт дубликаты;
- ошибка записи не оставляет в интерфейсе неподтверждённое состояние;
- импорт, удаление и смена тренировки по-прежнему обновляют все зависимые данные;
- ответ для ранее выбранной тренировки не заменяет данные текущей;
- одинаковое наблюдаемое поведение сохранено для IndexedDB и SQLite.

Изменение интерфейса репозитория считается архитектурным решением и перед
реализацией согласуется отдельно.

## Этап 2. Линейная агрегация и сокращение повторных обходов

Сейчас IndexedDB-репозиторий для каждой тренировки повторно фильтрует общие
массивы связей и подходов при расчёте статистики. Повторные поиски и фильтрации
есть также при сборке выбранной тренировки и поиске предыдущих подходов.
Нужно оценить эти операции по отдельности и в проблемных сценариях группировать
данные по идентификаторам один раз на прочитанный снимок. Достаточно временных
`Map` в рамках запроса; сохранять вычисленные индексы между запросами не нужно.

Критерии готовности:

- агрегация статистики линейна относительно прочитанных записей, сортировка
  итоговых точек учитывается отдельно: `O(W + R + S + P log P)`, где `W` — число
  тренировок, `R` — связей упражнений, `S` — подходов, `P` — итоговых точек;
- сборка тренировки и пакетный поиск предыдущих подходов используют группировку
  вместо повторного обхода всех подходов для каждого упражнения, если эти
  операции выбраны для оптимизации по измерениям;
- результат полностью совпадает с текущим для активных и архивных упражнений;
- сохраняются порядок подходов, выбор ближайшей более ранней заполненной
  тренировки, отсутствие предложения при заполненном упражнении или без истории;
- дробный вес и объём не округляются;
- контрактные и репозиторные тесты покрывают большую и разреженную историю;
- формат хранения и резервной копии не меняется.

## Этап 3. Ограничение стоимости длинных списков и графика

Этот этап выполняется только при подтверждённой просадке отрисовки. Возможные
меры рассматриваются по отдельности:

- отрисовка всей линии графика одним графическим контуром с сохранением всех
  исходных точек; отдельно измеряется стоимость маркеров точек;
- виртуализация списка дат тренировок;
- виртуализация подробной таблицы значений под графиком;
- сворачивание таблицы или сокращение видимых точек только тогда, когда меры
  с сохранением полного отображения недостаточны.

Изменение набора видимых точек или навигации по истории меняет поведение
продукта, поэтому конкретный вариант сначала согласуется и фиксируется в
`docs/product.md`.

Если требуется сокращение точек, до реализации определяется правило отбора:
сохраняются первая и последняя точки, глобальный минимум и максимум, а для
локальных пиков и провалов задаются проверяемые правила сохранения. Масштаб осей
вычисляется по полным данным, точные значения всей истории остаются доступны
в таблице. Правило проверяется отдельно для обеих метрик и короткой истории.

Критерии готовности:

- уменьшается измеренная стоимость отрисовки проблемного сценария; фиксируются
  число смонтированных элементов и способ его ограничения для выбранного решения;
- при замене способа отрисовки без сокращения точек сохраняются все точки и
  геометрия линии, при сокращении выполняется согласованное правило отбора;
- полная история остаётся доступной пользователю и средствам доступности;
- внешний вид проверен на узком экране iPhone в обычном и офлайн-режиме PWA.

## Этап 4. Нормализованное хранилище IndexedDB — условный

Текущая web-реализация хранит один версионированный снимок и при изменении
перезаписывает его целиком. Переход к отдельным object store и индексам нужен
только тогда, когда после применимых простых мер измерения показывают, что
сценарий выходит за бюджет именно из-за чтения или перезаписи полного снимка.
Выполнение этапа 3 не является обязательным условием: оптимизация графика
не устраняет задержку записи.

До реализации требуется отдельное архитектурное решение со следующими
обязательными условиями:

- атомарная миграция существующего снимка без потери данных;
- сохранение версии и совместимости формата экспорта;
- резервная копия до рискованной миграции и понятное восстановление при ошибке;
- индексы по тренировке, упражнению, позиции и связям подходов;
- тесты обновления существующей установленной PWA;
- тесты прерывания миграции и повторного запуска: сохраняется целостный прежний
  или новый набор данных, повторная попытка не дублирует записи;
- определённое поведение при открытой старой версии PWA, блокирующей обновление
  базы, и при запуске старого кэшированного приложения после миграции; старый
  код не должен записывать данные по несовместимой схеме;
- ручная проверка онлайн-обновления, офлайн-запуска и обратного экспорта на
  iPhone.

Без подтверждённых измерений этот этап не начинается.

## Порядок выполнения

1. Подготовить изолированные воспроизводимые наборы, снять базовые измерения
   и зафиксировать численные бюджеты и разброс.
2. По измерениям выбрать небольшие изменения этапов 1–2. Начать с повторных
   чтений, включая предложения копирования, если они определяют задержку;
   при преобладании вычислений сначала сократить повторные обходы.
3. После каждого изменения повторить измерения. Остановиться, если все сценарии
   укладываются в бюджеты, иначе определить оставшуюся причину задержки.
4. При проблемах отрисовки выбрать меры этапа 3; при дорогом чтении или
   перезаписи снимка после простых исправлений рассмотреть этап 4. Эти этапы
   независимы и не требуют обязательного выполнения друг друга.

Каждый этап завершается основной проверкой репозитория, целевыми тестами,
production web-сборкой и ручным сценарием установленной PWA на iPhone. Результаты
измерений и оставшиеся ограничения добавляются в `docs/checkpoint.md`.
